# Система учёта расходов

Личные финансы: пользователи, счета, категории и расходные операции.
Сайт и консоль работают с общей SQLite через Django ORM.

## Возможности

- Добавление и редактирование пользователей, счетов, категорий и расходов.
- Поиск по описанию, пользователю, счёту и категории; фильтры по дате,
  месяцу и статусу; сортировка и постраничный вывод.
- Проверка владельца счёта, доступного остатка, суммы и даты расхода.
- Перенос расхода на другой счёт с пересчётом обоих остатков.
- Статусы «Запланирован», «Оплачен» и «Отменён».
- Отмена расхода с возвратом денег без удаления истории.
- Статистика по категориям, пользователям, месяцам и статусам.
- Изображения счетов, понятные ссылки на карточки, административная панель.
- Перенос прежних JSON или SQLite в новую базу без повторного списания.

## Запуск

Нужны Python 3.11–3.14 и SQLite 3.37+. Инструкция для Arch Linux,
Ubuntu/Debian и обновления существующей установки: [LINUX_SETUP.md](LINUX_SETUP.md).

Windows / PowerShell, из каталога с `manage.py`:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py import_legacy
.\.venv\Scripts\python.exe manage.py runserver
```

Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py import_legacy
.venv/bin/python manage.py runserver
```

Открыть <http://127.0.0.1:8000/>. Команда `import_legacy` необязательна:
она добавляет исходные демонстрационные данные в пустую базу.
Все 3 пользователя, 4 счёта, 5 категорий и 9 операций в `data/*.json` вымышлены.
Повторный импорт в непустую базу завершается отказом, не меняя данные.
Новые расходы записываются сразу в SQLite; повторять импорт после них не нужно.

Для `/admin/` создать собственную учётную запись:

```bash
.venv/bin/python manage.py createsuperuser
```

В PowerShell использовать `.venv\Scripts\python.exe` вместо `.venv/bin/python`.
Готовых паролей в проекте нет. `users.User` — владелец финансовых счетов;
учётная запись Django для входа в админку — отдельная модель.

## Существующие данные

Новая база по умолчанию — `data/ledger.sqlite3`. Старую `data/expenses.sqlite`
не следует подменять ей и применять к ней миграции без переноса.
Для импорта старой SQL-версии после `migrate`:

```bash
.venv/bin/python manage.py import_legacy --database-source data/expenses.sqlite
```

Для четырёх JSON-файлов из другого каталога:

```bash
.venv/bin/python manage.py import_legacy --data-dir /path/to/json
```

Источник открывается только для чтения. Остатки переносятся как текущие:
исторические операции получают статус «Оплачен», но не списывают деньги повторно.
При ошибке импорт откатывается целиком. Формат самой ранней версии с одним
`expenses.json` отличается; этот файл нужно сохранить отдельно, он не подходит
для команды импорта четырёх сущностей.

## Деньги и статусы

В базе суммы — целые копейки, в формах — рубли с двумя десятичными знаками.
Например, `750,50` соответствует `75050` копейкам.

- Запланированный расход не меняет баланс; для него разрешена будущая дата.
- Оплаченный расход списывает деньги. Будущая дата оплаченного расхода запрещена.
  Исторические расходы добавлять можно.
- Отменённый расход остаётся в истории, возвращает ранее списанную сумму
  и исключается из итоговых расходов. Повторная отмена не возвращает деньги дважды.

Изменение суммы, статуса или счёта операции и пересчёт остатков выполняются
в одной транзакции. Проверки есть в формах и в модели; админка использует те же формы.
У счёта с операциями нельзя менять владельца. Счета, категории и пользователи,
на которые ссылаются операции, защищены от удаления через `PROTECT`.
Для удаления самой операции её сначала нужно отменить.
Массовый `Operation.objects.update()` запрещён, поскольку он обошёл бы пересчёт.
`bulk_create()` используется только для проверенного импорта исторических записей.

## Страницы

| Адрес | Назначение |
| --- | --- |
| `/` | Обзор остатков и последних расходов |
| `/accounts/` | Счета и фильтр по остатку |
| `/accounts/new/` | Новый счёт |
| `/accounts/by-name/<slug>/` | Счёт и его операции |
| `/operations/` | Поиск, фильтры, сортировка, страницы |
| `/operations/new/` | Новый расход |
| `/operations/<id>/edit/` | Изменение расхода |
| `/operations/statistics/` | Суммы и распределение расходов |
| `/users/`, `/categories/` | Справочники с формами изменения |
| `/admin/` | Управление данными |

Отмена выполняется только POST-запросом с CSRF-токеном.
Старые ссылки `/accounts/<id>/` продолжают работать.
В общем списке скрыты отменённые расходы; для их просмотра выбрать статус
«Все» или «Отменён». Размер страницы — 5 записей. Сумма над таблицей относится
ко всей отфильтрованной выборке оплаченных расходов, а не только к текущей странице.

## Структура

```text
ledger/                  ORM-модели, QuerySet, запросы, формы, админка
ledger/migrations/       схема и миграция нормализованных имён категорий
ledger/management/       импорт прежних данных
homepage/                обзор, справочники и статические файлы
accounts/                страницы счетов
operations/              страницы расходов и статистика
expense_tracker/         настройки и маршруты Django
templates/               общий каркас, фильтры и навигация
main.py                  консоль с той же базой ORM
models/, storage.py      чтение прежнего объектного JSON-формата
db/, sql/                прежняя SQL-версия и инструменты чтения её данных
tests/                   модели, перенос, формы, страницы и финансовые правила
```

Веб-представления используют `ledger`, а не `db.repository`.
Старые модули сохранены для совместимости с источниками импорта и историей проекта.
Подробное устройство: [GUIDE.md](GUIDE.md). Примеры запросов: [CODE_GUIDE.md](CODE_GUIDE.md).

## Проверки

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python -m pytest -q
.venv/bin/python -m flake8
```

Тесты используют временные базы и не меняют рабочие данные.
Для анализа запросов в локальной разработке:

```bash
DJANGO_DEBUG_TOOLBAR=1 .venv/bin/python manage.py runserver
```

В PowerShell: `$env:DJANGO_DEBUG_TOOLBAR="1"`, затем обычный запуск сервера.
На вкладке SQL можно сравнить запрос списка, подсчёт страниц и запрос карточки.
Таблица расходов получает сокращённый набор полей через `values()` с аннотациями
`F` связанных названий. Карточка расхода использует `select_related()`.
Отдельного запроса к владельцу для каждой строки нет.

## Настройки

- `DJANGO_DB_PATH` — путь новой базы ORM; по умолчанию `data/ledger.sqlite3`.
- `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS` — настройки Django.
- `DJANGO_DEBUG_TOOLBAR=1` — панель анализа SQL при `DEBUG=True` на localhost.
- `MEDIA_ROOT` — каталог загруженных изображений; по умолчанию `media/`.

Приложение рассчитано на локальную работу. Вход защищает административную
панель; отдельной регистрации и разграничения доступа к финансовым данным на сайте
пока нет. Перед публичным размещением нужны аутентификация, права доступа и настройки
продакшена. Для резервной копии сохраняются база SQLite и каталог `media/`.

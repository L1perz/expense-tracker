# Система учёта расходов

Индивидуальный проект, **вариант 14**. Сущности: пользователь, операция,
категория, счёт. Проект продолжает ПР1–ПР3 и реализует веб-часть ПР5–ПР7.

Возможности:

- создание пользователей, счетов, категорий и расходов через консоль;
- контроль владельца счёта, положительной суммы и достаточного остатка;
- просмотр счетов, пользователей, категорий и расходных операций на сайте;
- карточки счёта и операции со связанными данными;
- поиск операций по месяцу, пользователю, категории и фрагменту описания;
- поиск счетов по максимальному остатку;
- статистика по категориям, пользователям и месяцам, отбор категорий по сумме;
- обработка пустых результатов, неверных фильтров, отсутствующих объектов;
- сохранение объектов в JSON и перенос данных в SQLite.

## Быстрый запуск в Windows / PowerShell

Нужны Python **3.11+** и SQLite **3.37+** в составе Python (для STRICT-таблиц).
Проверено на Python 3.12.14, SQLite 3.53.1, Django 5.2.18.

Выполняйте команды из корня этого репозитория, где находится `manage.py`:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m db.import_json
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py runserver
```

Откройте <http://127.0.0.1:8000/>. Активация окружения и изменение
ExecutionPolicy не требуются. Миграции Django на этом этапе не нужны.
Остановка сервера — `Ctrl+C`.

Импорт выполняется один раз. Если база уже содержит данные, команда завершится
с понятным сообщением и сохранит их. Для сознательного обновления базы из JSON:

```powershell
.\.venv\Scripts\python.exe -m db.import_json --replace
```

`--replace` **заменяет все четыре таблицы** текущим содержимым JSON-файлов.
Удаления и вставки выполняются в одной транзакции: при ошибке старые строки
восстанавливаются. Перед импортом проверяются классы, ссылки и уникальность ID.
При отсутствии базы сайт показывает страницу с кодом 503.

В `data/` включены **вымышленные демонстрационные данные**: 3 пользователя,
4 счёта, 5 категорий, 9 операций за сентябрь и октябрь 2026 года.
Файл `data/expenses.sqlite` создаётся импортом и не хранится в Git.

## Консольная версия ПР3

```powershell
.\.venv\Scripts\python.exe main.py
```

Меню позволяет создавать сущности, записывать расходы, просматривать данные
и получать месячный отчёт. Пустой начальный баланс разрешён; нулевой расход
запрещён. Категории проверяются на повторение без учёта регистра.

**Два хранилища разделены по этапам работ:** консоль читает и изменяет JSON;
веб-часть ПР7 читает SQLite. После изменения данных в консоли выполните импорт
с `--replace`, чтобы обновить сайт. Автоматической двусторонней синхронизации нет.
Веб-формы здесь служат поиску и фильтрации; создание и редактирование данных
на сайте, аутентификация и Django ORM относятся к следующим этапам.

## Страницы

| Адрес | Назначение |
| --- | --- |
| `/` | Общий баланс, сумма расходов, последние операции |
| `/accounts/` | Счета и фильтр по остатку в рублях |
| `/accounts/1/` | Счёт, владелец и расходы по счёту |
| `/operations/` | История расходов и форма поиска |
| `/operations/1/` | Операция, дата, пользователь, счёт и категория |
| `/operations/statistics/` | Расходы по категориям, пользователям и месяцам |
| `/users/` | Пользователи |
| `/categories/` | Категории |

Примеры фильтров:

- `/operations/?month=2026-09` — сентябрь 2026 года;
- `/operations/?user_id=2&category_id=3` — расходы Анны на дом;
- `/accounts/?max_balance=8000` — счета с остатком до 8000 рублей;
- `/operations/statistics/?month=2026-10&min_total=1000` — категории с расходами
  от 1000 рублей за октябрь. Порог применяется к категориям; остальные показатели
  относятся ко всему выбранному периоду. Динамика по месяцам показывает всю историю.

Фрагмент описания ищется с учётом регистра. Даты и суммы проверяются на сервере.
Некорректные фильтры возвращают HTTP 400, отсутствующие объекты — HTTP 404.

## Предметная модель и формат данных

| Класс | Атрибуты | Поведение |
| --- | --- | --- |
| `User` | `id`, `name` | Проверка имени, строковое представление, сериализация |
| `Account` | `id`, `user`, `name`, `balance` | Проверка остатка и списание `withdraw()` |
| `Category` | `id`, `name` | Проверка названия, строковое представление |
| `Operation` | `id`, `user`, `account`, `category`, `amount`, `date`, `description` | Проверка владельца и суммы, представление и сериализация |

Связи в Python являются ссылками на объекты. В JSON хранятся их ID.
`storage.load_project()` восстанавливает общие объекты и ссылки между ними.
Конструктор `Operation` не списывает деньги: списание производится только
при создании нового расхода функцией `create_operation()`.

Все суммы — **целые копейки**, без `float`. Ввод рублей разбирается через
`Decimal`, в том числе с десятичной запятой. Даты в JSON и SQLite — `YYYY-MM-DD`;
в объектах Python используется `datetime.date`.
Баланс JSON и SQLite — уже текущий остаток, не начальная сумма до всех расходов.

## Схема SQLite

| Таблица | Поля |
| --- | --- |
| `users` | `id INTEGER PRIMARY KEY`, `name TEXT` |
| `accounts` | `id INTEGER PRIMARY KEY`, `user_id INTEGER`, `name TEXT`, `balance INTEGER` |
| `categories` | `id INTEGER PRIMARY KEY`, `name TEXT UNIQUE` |
| `operations` | `id INTEGER PRIMARY KEY`, `user_id INTEGER`, `account_id INTEGER`, `category_id INTEGER`, `amount INTEGER`, `date TEXT`, `description TEXT` |

Все поля обязательны. Внешние ключи: счёт → пользователь, операция →
пользователь и категория. Составной внешний ключ `(account_id, user_id)` →
`accounts(id, user_id)` дополнительно гарантирует принадлежность счёта
пользователю операции. Ограничения `CHECK` запрещают отрицательный баланс,
неположительный расход, пустые названия и некорректные даты.

Внешние ключи включаются на каждом подключении. `sqlite3.Row` позволяет читать
поля по именам. Соединения закрываются после выполнения запросов.
SQL хранится в одном файле `sql/queries.sql`, а `db/repository.py` загружает
его и передаёт параметры отдельно от текста запросов.

| Группа | Запросы в `sql/queries.sql` | Где используются |
| --- | --- | --- |
| Простые списки | 01 `users`, 02 `categories` | Справочники и формы фильтрации |
| Фильтрация `WHERE` | 04 `low_balance_accounts`, 07 `filtered_operations` | Счета и поиск операций |
| Соединения `JOIN` | 03 `accounts`, 06 `operations` | Списки, обзор и история |
| Агрегаты | 09 `expense_summary`, 10 `balance_summary` | Обзор и статистика |
| `GROUP BY` | 11 `category_totals`, 12 `user_totals`, 13 `monthly_totals` | Статистика |
| `HAVING` | 11 `category_totals` | Порог расходов категории |
| Карточки | 05 `account`, 08 `operation` | Детальные страницы |

Путь данных: `URL → view → db.repository → sqlite3 → SQLite → context → template`.

## Проверка

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe -m pytest -v
.\.venv\Scripts\python.exe -m flake8
```

Тесты используют отдельные временные базы; рабочие данные не изменяются.
Проверяются денежные ограничения, отношения объектов, JSON, запросы,
внешние ключи, откат импорта, фильтры, экранирование HTML и обработчики ошибок.

## Настройки

Для локального запуска настройки уже готовы. Необязательные переменные среды:

- `DJANGO_DEBUG=0` — отключить отладочную страницу для проверки своей 404;
- `DJANGO_ALLOWED_HOSTS` — допустимые хосты через запятую;
- `DJANGO_SECRET_KEY` — ключ окружения при развёртывании;
- `EXPENSE_DB_PATH` — путь к SQLite для веб-части и команды импорта;
- `EXPENSE_DATA_DIR` — каталог данных в настройках Django.

Команда импорта также принимает `--data-dir` и `--database`. Если исходные
JSON находятся в другом каталоге, передайте `--data-dir` явно.
Настройки по умолчанию предназначены для локальной учебной разработки.
Bootstrap подключён отдельно; собственный CSS обеспечивает основную раскладку
и работает без загрузки Bootstrap из сети.

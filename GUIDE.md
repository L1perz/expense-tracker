# Устройство приложения

## Данные

`users.User` владеет счетами `Account`. Расход `Operation` связан с пользователем,
счётом и категорией `Category`. Связи используют `ForeignKey(PROTECT)` и обратные
имена `accounts` и `operations`. Модели наследуют `django.db.models.Model`.
Каждая сущность имеет своё Django-приложение: `users/models.py`,
`categories/models.py`, `accounts/models.py`, `operations/models.py`.
`ledger` содержит общие запросы, обработчики и команду импорта. Его `models.py`
сохраняет совместимые импорты прежних путей, но не определяет модели.

Таблицы по-прежнему называются `ledger_user`, `ledger_category`, `ledger_account`
и `ledger_operation`: явный `Meta.db_table` позволяет перенести модели без
пересоздания таблиц. Начальные миграции приложений обновляют состояние Django
через `SeparateDatabaseAndState`; `ledger.0003` завершает перенос и обновляет
ContentType. Сохраняются ID типов, права пользователей и групп, журнал админки,
ID записей, балансы, slug и пути изображений. Старые миграции не изменены.
Обновление существующей базы и откат проверяются в `tests/test_migrations.py`.

Идентификаторы формирует Django. Все суммы хранятся целыми копейками.
Формы преобразуют рубли через `Decimal`. Поле `Operation.is_large` вычисляет
база через `GeneratedField`: оно истинно для суммы от 10 000 рублей.

`Category.name_key` хранит `name.strip().casefold()` с уникальным ограничением.
Так категории «Еда» и «ЕДА» не дублируются даже с учётом ограниченной поддержки
Unicode в функциях сравнения SQLite. Миграция `0002` заполняет ключи существующих
категорий до введения уникального ограничения.

## Учёт денег

Начальный баланс задаётся при создании счёта. `Account.save()` при редактировании
пишет только реквизиты: название, владельца, slug и изображение. Остаток исключён
из `UPDATE` и перечитывается после сохранения, поэтому старый экземпляр счёта
не отменит уже проведённое списание. Явный `save(update_fields=['balance'])`
отклоняется; денежные изменения выполняет механизм операций.

`Operation.save()` в `transaction.atomic()` читает сохранённую операцию,
возвращает её прежнюю оплаченную сумму и списывает новую. Изменения объединяются
по счетам; при редактировании без изменения суммы итоговая поправка равна нулю.
Счета блокируются в одинаковом порядке. Проверка текущего остатка при `UPDATE`
не позволяет молча перезаписать параллельное изменение.

На SQLite `select_for_update()` сам по себе не создаёт построчную блокировку:
здесь также используются транзакция, условное обновление остатка и ограничения БД.
При конфликте записи клиент получает ошибку и может повторить действие.

Планирование не списывает деньги. Оплата списывает. Отмена возвращает ранее
списанную сумму один раз и сохраняет запись в истории. `cancel()` сначала
перечитывает операцию внутри транзакции: сумма, счёт и описание берутся из
актуальной записи, даже если вызывающий объект загружен до её редактирования.
Будущая дата разрешена
для плана, прошедшая дата разрешена для уже совершённого расхода.
Одна и та же сумма и дата у двух покупок допустимы: это не бронирования.

## Страницы и формы

Путь запроса: `URL → view → Form/ModelForm → ORM → шаблон`.
`ledger/queries.py` содержит сводки и группировки, `OperationQuerySet` —
повторно используемые условия и загрузку связей. `operations/forms.py` проверяет
GET-параметры; `ledger/forms.py` создаёт и изменяет модели.

GET показывает форму. POST связывает её с данными и файлами. После проверки
`is_valid()` вызывается `form.save()`, затем перенаправление на карточку.
При ошибке остаются введённые значения, ошибки поля и общие ошибки формы.
Редактирование передаёт `instance`, поэтому меняется существующая запись.
При проверке остатка форма учитывает уже списанную сумму редактируемого расхода.

`ledger/views.py` содержит общие обработчики небольших справочников и форм.
Удаление справочника начинается со страницы подтверждения; само удаление — POST.
Отмена расхода принимает только POST. Все формы изменения содержат CSRF-токен.

Список расходов поддерживает фильтры, разрешённые варианты сортировки и `Paginator`.
`ledger.queries.operation_rows()` добавляет через `F` имена связанных сущностей
и slug счёта, а через `Case` — подпись статуса, затем выбирает только поля таблицы
через `values()`. В шаблон передаются словари; ссылки строятся тегом `url` по ID
операции и slug счёта. Срез выполняется базой после фильтрации и сортировки.
Обзор и карточка счёта используют тот же формат строк; подробная карточка расхода
и формы получают объект модели через `select_related()`.
При смене страницы сохраняются GET-параметры. Неизвестная сортировка даёт HTTP 400;
неверный номер страницы обрабатывается `get_page()`. Нет объекта — HTTP 404.

Поиск списка расходов сравнивает `casefold()` запроса и четырёх полей: описания,
названия счёта, категории и имени пользователя. `ledger/db_functions.py` добавляет
функцию `UNICODE_CASEFOLD` в каждое подключение SQLite через `connection_created`.
Нормализация выполняется в запросе, поэтому изменения связанных названий видны
сразу и отдельный поисковый индекс синхронизировать не нужно. Параметры и символы
`%`, `_`, `\\` обрабатываются стандартным ORM `contains` как обычный текст.

## Управление

`users/admin.py`, `categories/admin.py`, `accounts/admin.py`, `operations/admin.py`:
четыре модели, столбцы, поиск по связанным именам, фильтры,
сортировка, разбиение списка на страницы. Inline показывает связанные операции
и ссылки на их редактирование; финансовые записи не меняются произвольно внутри inline.
Операция и категория в админке редактируются теми же формами, что и на сайте.
`CategoryForm` показывает дубль названия как ошибку поля до сохранения модели;
уникальность нормализованного ключа дополнительно защищена в базе.
`ledger/admin.py` содержит общую базу `UnicodeSearchAdmin` и название панели.
Все четыре списка админки используют общий Unicode-поиск из
`ledger/db_functions.py`: регистр кириллицы учитывается так же, как на сайте.
Несколько слов запроса объединяются через AND, фраза в кавычках ищется целиком;
поиск сохраняет выбранные фильтры административного списка.
Счёт открывается по `slug`; ссылка строится через `get_absolute_url()` и `reverse()`.
В формах счёта и админке поддерживается загрузка `ImageField`.

Общие подписи передаются через `ledger/context_processors.py`.
SQL можно посмотреть в Debug Toolbar при `DJANGO_DEBUG_TOOLBAR=1`.

## Перенос

Миграции создают новую `data/ledger.sqlite3`. Старые таблицы не переименовываются
на месте. Команда `import_legacy` переносит проверенные JSON или старую SQLite
в пустую базу. Сохраняются ID, связи, текущие остатки и исторические суммы.
Вставка исторических операций не вызывает обычное списание.

Прежние `models/`, `storage.py`, `db/` и `sql/` описывают форматы прежних версий.
Они не обслуживают текущие веб-страницы. Консоль `main.py` использует ORM.

## Проверки

`tests/test_orm.py` проверяет расход, изменение суммы и счёта, отмену,
недостаточный баланс, чужой счёт, дату, статусы, миграцию данных,
CSRF, изображения, админку и отсутствие N+1 при загрузке объектов.
`tests/test_web.py` проверяет маршруты, фильтры, пустые результаты и ошибки.
`tests/test_review_regressions.py` проверяет устаревший счёт и отмену расхода,
дубли категорий при создании и изменении в админке, поиск Unicode во всех четырёх
полях, буквальные спецсимволы и регистрацию функции при новом подключении.
Тесты прежнего JSON и SQL сохранены для контроля совместимости импорта.

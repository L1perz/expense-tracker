# Практические работы и подготовка к защите

## Что исправлено

На исходной вершине `main` (`f8a1add`) работали четыре теста функциональной
версии ПР2. Классы ПР3 были в более ранней истории (`d071f38`), но в последнем
состоянии репозитория исчезли: `expense_tracker/__init__.py` содержал только
заглушку. README при этом продолжал заявлять наличие ООП.

В актуальной версии восстановлены классы и взаимодействие объектов,
добавлены ПР5–ПР7. Код предметной области вынесен в `models/`, конфигурация
Django — в `expense_tracker/`, веб-приложения — в отдельные каталоги.
Скриншот варианта определяет именно **четыре сущности**, а не структуру папок.
Структура адаптирована к варианту 14 по примерам практических работ.

Дополнительно исправлены:

- приём `NaN`, бесконечностей, слишком больших и неточных денежных значений;
- запрет нулевого баланса нового счёта при разрешении такого баланса моделью;
- поиск месяца по неполному префиксу вместо проверки `YYYY-MM`;
- некорректный вывод отрицательных денежных значений;
- отсутствие проверки структуры JSON, дубликатов ID и нарушенных ссылок;
- риск повторного списания при восстановлении исторических операций;
- конфликт имён файлов старой версии с Django-приложениями.

## Последовательность демонстрации

1. Выполнить команды из README: импорт базы, `manage.py check`, тесты, flake8.
2. Открыть `/`: общий баланс **193258.00 руб.**, расходы **10859.50 руб.**,
   **9 операций** на исходных демонстрационных данных.
3. Перейти в «Счета», открыть «Основная карта»: владелец Лев,
   текущий баланс **42658.00 руб.**, только операции этого счёта.
4. В списке счетов указать максимальный остаток `8000`: останутся «Наличные».
5. В «Операциях» выбрать сентябрь 2026: две операции, сумма **1160.00 руб.**
6. Сбросить форму, выбрать пользователя Анна и категорию «Дом»:
   одна операция «Коммунальные услуги».
7. Открыть карточку операции: показать дату, владельца, ссылку на счёт,
   категорию и описание. Объяснить JOIN четырёх таблиц.
8. В «Статистике» выбрать октябрь 2026 и порог категории `1000`:
   останутся «Дом» и «Продукты». Пользователь Михаил отображается с нулём.
9. Проверить пустую выборку месяца `2000-01` и `/operations/999/`.
10. Показать в коде маршрут, view, именованный запрос, параметры и шаблон.

Свой обработчик 404 включается при `DEBUG=False`. Тесты проверяют именно
этот режим. Для ручной проверки в PowerShell:

```powershell
$env:DJANGO_DEBUG = "0"
.\.venv\Scripts\python.exe manage.py runserver --insecure
```

`--insecure` нужен только для локальной проверки статики при выключенной отладке.
После проверки остановите сервер и удалите временную переменную:

```powershell
Remove-Item Env:DJANGO_DEBUG
```

## Что важно понимать

- `expense_tracker/` — конфигурационный пакет Django; `accounts/` и
  `operations/` — приложения. `models/` — обычная объектная модель ПР3.
- `Account.withdraw()` относится к поведению конкретного счёта.
  `filter_operations()` относится к коллекции и остаётся функцией.
- Историческая операция создаётся без списания; новый расход создаётся
  через `create_operation()`, которая проверяет остаток и списывает сумму.
- JSON хранит ID связанных объектов. При чтении `storage.load_project()`
  связывает операцию с уже созданными объектами пользователя, счёта и категории.
- `render()` объединяет шаблон с контекстом и возвращает HTTP-ответ.
  HTML не собирается Python-строками в окончательной версии.
- `{% extends %}` задаёт каркас, `{% block %}` — заменяемую часть,
  `{% include %}` — повторно используемый фрагмент.
- `{% url %}` и `app_name` связывают шаблоны с именованными маршрутами;
  `<int:operation_id>` отсекает текстовые идентификаторы.
- Пустой результат SQL — нормальная ситуация. В шаблоне используется
  `{% empty %}`; отсутствие конкретного объекта даёт HTTP 404.
- `WHERE` отбирает строки до группировки, `HAVING` — группы после неё.
  `COUNT(o.id)` при LEFT JOIN даёт ноль для категории без операций.
- Параметры SQL передаются словарём вторым аргументом `execute()`.
  В пользовательские значения не встраиваются ни f-строки, ни конкатенация SQL.
- Интерфейс работает с понятиями предметной области; SQL виден только в коде.
- На этапе ПР7 сайт читает SQLite, консоль изменяет JSON. Обновление сайта
  после консольных изменений требует явного повторного импорта.
